이 프로젝트는 납품이 끝났습니다. 포트폴리오 제작에 쓸 재료를 만들어 주세요.
당신이 만든 압축 파일 하나만 담당자에게 전달되고, 문안·색 변경·게시는 담당자가 합니다.

■ 먼저 확인 — 이 절차가 맞는 프로젝트인가

  화면이 있는 서비스(웹앱·관리자·PWA)를 로컬에서 띄울 수 있어야 합니다.
  배치·CLI·데이터 파이프라인·모바일 네이티브처럼 **띄워서 찍을 화면이 없으면 진행하지 말고**
  저에게 알려 주세요. 담당자와 상의가 필요합니다.

  **어느 시점을 찍을지 먼저 확정하세요.** 특정 납품 시점(태그·릴리스)만 쓸 거면 그 커밋을 별도
  작업 폴더로 꺼내 띄웁니다. 현재 개발 브랜치를 그대로 쓰면 그 시점에 없던 기능이 섞입니다.
  작업 폴더는 **세션이 끝나도 사라지지 않는 위치**에 두세요(임시·스크래치 디렉터리는 청소됩니다).

■ 어떻게 할지는 당신이 정하세요

  로컬 스택을 띄우는 법, 데이터를 바꾸는 법, 화면을 찍을 도구 — 이 레포에 맞는 방법을 고르세요.
  레포에 이미 있는 것을 먼저 쓰는 편이 빠릅니다(e2e 설정, 시드 스크립트, 개발 서버 명령).
  아래 "절대 규칙"과 "판정 기준"만 지키면 방법은 자유입니다.

  **촬영은 반드시 스크립트로 하세요.** 데이터가 어긋나거나 화면이 잘려 다시 찍는 일이 반드시
  생깁니다. 화면 몇 장만 다시 찍을 수 있게 나눠 두면 왕복 비용이 크게 줄어듭니다.
  여러 스크립트가 같은 파일명을 쓰면 **나중에 실행한 쪽이 앞의 결과를 덮어씁니다.** 재촬영 뒤에는
  파일 단위로 최종 상태를 다시 확인하세요.

■ 절대 규칙

  · **운영에 닿지 않습니다.** 접속은 localhost / 127.0.0.1 만. 운영·스테이징 주소나 원격 DB 금지.
    ssh 터널·포트포워딩으로 운영에 연결된 로컬 주소라면 저에게 먼저 확인하세요.
    **예외**: 앱이 관리형 클라우드 DB(Supabase·Firebase 류) 없이는 뜨지 않는 구조라면, 클라이언트
    데이터가 전혀 없는 **새 프로젝트를 따로 만들어** 쓰는 방법을 저에게 제안하고 승인을 받으세요.
    기존 개발·검수·운영 DB에 붙는 것은 승인 대상이 아니라 금지입니다. 승인받아 쓴 경우 report.json 에
    `"dbUrlRemoteReason": "촬영 전용으로 새로 만든 Supabase 프로젝트 — 클라이언트 데이터 없음"` 처럼
    **20자 이상의 사유를 이 필드에** 적으세요. notes 에만 적으면 받는 쪽 검사가 "운영 DB 캡처"로 보고 반려합니다.
  · **.env 를 먼저 확인합니다.** 운영 호스트나 결제·문자·메일·CMS 같은 외부 연동 키가 들어 있으면
    **거기서 멈추고 알려 주세요.** 그대로 실행하면 운영에 실제 요청이 나갑니다.
    진행할 때는 기존 .env 를 쓰지 말고 **캡처 전용 환경 파일을 새로 만들어** DB 주소·공개 키 등
    화면을 띄우는 데 꼭 필요한 값만 넣고, 메일·결제·알림 연동 값은 비워 두세요.
  · **그럴듯한 값을 지어내지 않습니다.** 아래 "가짜 데이터" 참고.
  · **화면 색을 바꾸지 않습니다.** 납품물 색 그대로 찍습니다. 색 분리는 담당자가 이미지에서 합니다.
    제품이 원래 어두운 테마면 그대로 두세요. 브라우저 컬러스킴만 light 로 고정합니다.
  · **문안(소개글·기능 설명)을 쓰지 않습니다.** 담당자가 공고·지원서를 보고 씁니다.
  · **레포 코드를 고치지 않습니다.** 화면에 박힌 클라이언트 자산 문구처럼 코드를 고쳐야만 바꿀 수
    있는 경우에만 임시로 고치고, 촬영이 끝나면 **되돌린 뒤 되돌아간 것을 확인**하고(예: 추적 파일
    변경 0건) report.json 의 repoChanges 에 파일별로 적으세요. 임시 수정 뒤에는 타입 검사·빌드로
    앱이 깨지지 않았는지 확인합니다.
  · **다음은 하기 전에 물어보세요**: 무거운 설치(Docker·브라우저 런타임 등), 이미 떠 있는 프로세스
    종료, 포트 강제 회수, 컨테이너·볼륨 삭제, DB 초기화, 유료 자원 생성.
    포트를 다른 프로젝트가 쓰고 있으면 그걸 죽이지 말고 **다른 포트로 따로 띄우는 편이 낫습니다**
    (레포 설정 파일을 고치는 대신 환경변수로 넘기세요).

■ 데이터 만들기 — 빈 DB에서 시작할 때

  · 레포에 적힌 **부트스트랩 절차를 먼저 찾으세요**(운영 이관 문서, 시드 파일 머리말, README).
    "시드 → 마이그레이션 → 시드 재실행" 처럼 순서가 정해진 경우가 많고, 그 순서를 지키지 않으면
    중간에서 멈춥니다. 콘텐츠를 다루는 마이그레이션이 기존 데이터를 전제하는 구조가 흔합니다.
  · **시드 파일이 최신이라고 믿지 마세요.** 납품 후 수정이 마이그레이션에만 들어가고 시드에는
    반영되지 않은 경우가 있습니다. 두 경로의 결과를 대조해 어느 쪽이 실제 납품 상태인지 판정하고,
    판정 근거를 notes 에 적으세요.
  · 목록·이력·제출 기록처럼 운영 중 쌓이는 데이터는 **앱을 실제로 조작해 만드는 편이 자연스럽습니다.**
    다만 폼 자동 채우기는 모든 칸에 같은 문장을 넣기 쉬우니, **필드 이름에 맞는 값**을 넣고 채운 뒤
    화면을 열어 문장이 말이 되는지 확인하세요.
  · **차트·드래그·연결·업로드처럼 텍스트 입력이 아닌 위젯은 자동 입력으로 채워지지 않습니다.**
    값이 0이거나 "미선택"으로 남은 화면은 빈 화면으로 반려됩니다. 저장 구조(스키마)를 확인해
    DB로 직접 채우되, 합계·개수·순위가 서로 맞게 넣으세요.
  · **조건이 맞아야 나타나는 목록**(만료 임박, 미납, 알림, 경고)은 그 조건을 만족하는 데이터를
    일부러 만들어야 화면이 찹니다.

■ 가짜 데이터 — 무엇이 "가짜"인가

  ⚠️ **이 프로젝트의 기존 시드를 믿지 마세요.** 데모 시드처럼 보여도 실제 상호·고객 이름이 들어 있는
     경우가 있습니다(실측 사례). 값을 직접 확인하고, 실물로 보이면 바꿉니다.

  바꿀 것: 사람 이름, 전화번호, 이메일, 회사·기관·건물·현장 이름, 주소, 사업자등록번호,
          **계좌번호·예금주**, 메모·비고 같은 자유 서술(실명·연락처가 섞여 있습니다).
  ⚠️ 사람·고객 테이블만 보지 마세요. **설정·환경값 테이블**(system_settings 류)에 수납 계좌·담당자
     이름이 문자열로 박혀 있는 경우가 있습니다(실측: "농협 301-…-51 홍길동"). 자유 텍스트 컬럼을
     전수로 훑어 실물로 보이는 값을 찾으세요. JSON 컬럼 안도 훑어야 합니다.
  두어야 할 것: 로그인 계정(바꾸면 캡처를 못 합니다), 은행명·반 이름 같은 라벨, 상태값·코드·ID.
  ⚠️ **이름·코드가 곧 로그인 수단인 시스템**(이름+번호로 입장, 초대 코드 로그인 등)에서는 값을 바꾼
     뒤 그 값으로 실제 로그인이 되는지 확인하고 촬영하세요.

  값은 **구조적으로 존재할 수 없어야** 합니다. "아마 없을 것"이 아니라 "있을 수 없음"입니다.
  그럴듯한 값을 떠올려 쓰면 그게 실존 값입니다 — 지어낸 주소가 실제 랜드마크 주소였던 사고가 있었습니다.

    전화번호   국번(가운데 자리)이 0 으로 시작. 예: 010-0123-4567, 02-0456-7890
               → 국내 번호 체계에서 0 으로 시작하는 국번은 배정되지 않습니다.
    사업자번호 검증코드가 **틀려야** 합니다. 앞 9자리에 가중치 [1,3,7,1,3,7,1,3,5] 를 곱해 더하고,
               9번째 자리×5 의 십의 자리를 더한 뒤 (10 - 합%10) % 10 이 올바른 검증코드입니다.
               그 값과 **다른 숫자**를 10번째 자리에 씁니다 → 등록될 수 없는 번호가 됩니다.
    이메일     example.com / example.kr 만 (RFC 2606 예약 도메인, 실존 불가).
    주소       실존하지 않는 조어 도로명. 실제로 있는 도로명(월드컵북로·올림픽로·테헤란로·강남대로 등)
               은 쓰지 않습니다.
    이름·상호  조어 조합. 인사·평가 화면이면 성만 남기고 마스킹(홍**)하는 편이 관행에 맞습니다.
               상호는 두 음절 이상 조합해 실존 가능성을 낮추세요.

  DB 를 쓰지 않는 프로젝트면 바꿀 데이터가 없을 수 있습니다. 그때는 scrub.tables 를 빈 배열로 두고
  notes 에 이유를 적으세요. 화면의 더미 텍스트에 실명·연락처가 있으면 그건 코드에서 바꿉니다.

  다 바꾼 뒤 **직접 검증하세요.** 스크립트로 모든 텍스트·JSON 컬럼을 훑어 아래를 찾습니다.
    ① 검증코드를 통과하는 사업자번호  ② 국번이 0 으로 시작하지 않는 전화번호
    ③ 실존 도로명  ④ 레포 문서·도메인에 나오는 발주처 이름  ⑤ example 계열이 아닌 외부 도메인 이메일

■ 콘텐츠 자산 — 화면 안의 "내용물"도 클라이언트 것입니다

  문제·지문·교재 문구·상품 설명·약관·커리큘럼처럼 **화면 안에 들어가는 콘텐츠는 대개 클라이언트
  자산**입니다. 개인정보가 아니어도 그대로 실으면 안 됩니다.

  · **UI·UX·화면 구성·조작 방식은 그대로 두고, 안에 들어가는 내용만 새로 만드세요.** 필드 개수·표
    구조·입력 방식·페이지 흐름을 바꾸면 우리가 만든 결과물이 아니게 됩니다.
  · 바꿀 것: 제목·단원/카테고리 이름, 문항 문장, 보기·선택지, 표 안의 데이터, 카드·키워드 세트,
    예시 답안, 안내 문구. 같은 값이 여러 화면에 퍼져 있으니 한 곳만 고치고 끝내지 마세요.
  · **파생 명칭까지 바꿔야 합니다.** 유형 이름·등급 이름·축 라벨처럼 원본 분류 체계에서 온 표현이
    차트 축, 표 머리글, 요약 카드에 함께 나옵니다. 하나라도 남으면 티가 납니다.
  · 바꾼 콘텐츠와 **기존 답안·통계가 서로 맞아야 합니다.** 보기를 바꿨으면 저장된 답도 새 보기로
    갱신하세요. 옛 값이 남으면 "미선택"이나 빈 칸으로 보입니다.
  · 콘텐츠 문구가 **코드에 하드코딩**된 경우가 많습니다(도움말·기본 라벨·안내문). 위 "절대 규칙"의
    임시 수정 절차를 따르고 repoChanges 에 적으세요.
  · 외부에서 가져오는 콘텐츠(유튜브 임베드, 외부 위젯)는 채널명·광고가 같이 찍힙니다. 그 화면은
    빼고 같은 기능을 보여 주는 다른 화면으로 대신하세요. 임베드만 비우면 검은 상자가 남습니다.

■ 규모 수치

  화면에 클라이언트의 실제 규모를 특정하는 숫자(대상 인원·설비 수·거래 건수·매출)가 보이면
  **실제보다 큰 라운드 넘버로 데이터를 늘립니다.** 예: 실제 47명 → 100명, 811명 → 1,000명.
  · 실제보다 작게 잡지 마세요 — 우리 작업이 과소평가됩니다(줄였다가 반려된 적 있습니다).
  · 화면 텍스트만 고치면 표 합계와 어긋납니다. **데이터부터 늘리고** 다시 찍으세요.
  · 상위·하위 관계(기관–반–인원, 회사–부서–직원)가 함께 보이면 **각 단계를 같이 늘려** 합계·평균·
    진행률이 맞아떨어지게 하세요. 한 단계만 늘리면 목록과 요약 숫자가 어긋납니다.
  · 무엇을 몇 → 몇으로 바꿨는지 report.json 의 scaleSynthesis 에 적으세요.

■ 화면 — 무엇을 찍는가

  · **많이 찍는 게 원칙입니다.** 고르는 건 담당자가 하고, 찍지 않은 화면은 나중에 만들 수 없습니다.
    로그인 후 갈 수 있는 화면을 두루 찍고, 링크로 못 가는 모달·탭·다단계 흐름도 조작해서 찍으세요.
    아주 많으면(60장 초과) 대표적인 것으로 추리고 무엇을 뺐는지 notes 에 적으세요.
  · **데이터가 찬 상태**로 찍습니다. "표시할 내역이 없습니다", 빈 표, "검색 결과 0건" 화면은 반려됩니다.
    외부 연동 응답이 있어야만 생기는 화면처럼 **채울 방법이 없으면 찍지 말고** notes 에 이유를 적으세요.
  · **모달·상세 패널은 "무엇을 골라야 내용이 나오는지" 확인하고 조작한 뒤 찍으세요.** 좌우 2단
    구조는 양쪽을 다 선택해야 내용이 뜨는 경우가 있습니다. 촬영 직전에 화면 텍스트를 읽어
    "선택해 주세요" 류 안내만 남아 있지 않은지 확인하고, 그래도 비면 그 화면은 빼세요.
  · 모바일은 **반응형인 화면만**. 가로로 넘치는 데스크톱 전용 화면은 세로에서 글자가 깨지므로 건너뜁니다.
  · **보이는 영역만 찍습니다(fullPage 금지).** 세로로 긴 이미지는 소개 이미지 프레임에 못 넣습니다.
  · **스크롤해서 찍을 때는 고정 헤더·탭·푸터 높이를 계산하세요.** 그냥 좌표로 스크롤하면 내용이
    헤더에 가려 잘립니다. 화면에서 고정(sticky/fixed) 요소들의 실제 높이를 재고, 보여 줄 블록의
    윗변이 그 아래에서 시작하도록 맞춘 뒤 촬영하세요. 스크롤 후 다시 맨 위로 올리는 처리가
    있으면 순서 때문에 무효가 되니 촬영 직전 위치를 확인합니다.
  · **라이트 모드·한국어로 찍습니다.**(브라우저 컬러스킴 light, 로케일 ko-KR 고정)
  · 같은 화면이 여러 번 찍히지 않게 하세요. **내용이 완전히 같은 스크린샷이 둘 이상이면 반려됩니다.**
    **파일 해시로 중복을 검사**하고, 해시가 달라도 내용이 같아 보이면(예: 상세로 못 들어가고 목록이
    다시 찍힘) 실제로 열어 확인하세요.
  · 개발 오버레이(에러 배지·devtools)를 숨기고, 애니메이션을 멈추고, 스크롤 위치를 정한 뒤 찍으세요.
  · **앱 자체의 에러·경고 배너나 환영 토스트가 떠 있으면 닫거나, 뜨지 않는 경로로 들어가 찍으세요.**
    (예: 로그인 직후 리다이렉트된 주소 대신 그 화면의 정상 주소로 다시 진입)
  · **발주처 로고·상호가 헤더·푸터·워터마크에 있으면 가리고 찍으세요**(그 요소를 숨기면 됩니다).
  · 앱이 보고서·계약서 같은 문서를 생성하면 실제로 생성해 이미지로 바꿔 materials/ 에 넣으세요.
  · 촬영이 끝나면 **대표 화면 몇 장을 실제로 열어 확인**하세요. 특히 새로 채운 데이터가 들어간 화면,
    모달, 차트 화면.

■ report.json

  ⚠️ 아래 `//` 는 설명용입니다. **실제 파일에는 주석을 넣지 마세요** — JSON 은 주석을 허용하지 않아
     받는 쪽에서 파싱이 깨집니다. 다 쓴 뒤 유효한 JSON 인지 한 번 확인하세요.

  {
    "slug": "260910_daycare-crm",
    "capturedAt": "2026-09-10T11:20:00+09:00",
    "baseUrl": "http://localhost:5174",
    "dbUrl": "postgresql://...@127.0.0.1:5433/…",     // 비밀번호는 *** 로 가리세요. DB 없으면 null
    "stack": ["React 18.3", "Vite 5", "Hono 4", "PostgreSQL 16"],   // 실제 버전
    "scale": {                                          // 레포에서 센 사실. 모르는 항목은 null
      "screens": 41, "apiRoutes": 156, "dbTables": 32, "migrations": 0, "tests": 254
    },
    "routes": [{ "path": "/dashboard", "title": "대시보드", "nav": "대시보드" }],
    "docs": ["README.md", "docs/02-FUNCTIONS.md"],      // 담당자가 읽을 만한 문서 경로
    "git": { "from": "2026-04-11", "to": "2026-09-03", "commits": 1355, "ref": "v1.2.0" },   // ref = 실제로 띄워 찍은 태그/커밋
    "scrub": {
      "tool": "무엇으로 바꿨는지 한 줄",
      "tables": [{ "table": "parents", "rows": 47, "columns": ["name","phone","email"] }],
      "verified": true,                                 // 위 ①~⑤ 검증을 통과했나
      "samples": {                                      // 실제로 써 넣은 값 몇 개씩 (담당자가 기계로 대조)
        "phone":   ["010-0123-4567"], "bizNo": ["123-45-67891"],
        "person":  ["홍**"], "org": ["가온어린이집"],
        "address": ["대전광역시 대덕구 나린대로 309"], "email": ["user1@example.com"]
      },
      "contentRewrite": [                               // 콘텐츠 자산을 바꿨으면. 없으면 생략
        { "what": "활동 문항·보기·표 데이터", "count": 247, "kept": "화면 구성·입력 방식" }
      ],
      "notes": ""
    },
    "scaleSynthesis": [{ "what": "회원 수", "from": 47, "to": 100 }],   // 없으면 []
    "screens": [
      { "name": "dashboard", "path": "/dashboard", "title": "대시보드",
        "viewport": "desktop", "textLength": 1840, "hasData": true }
    ],
    "mobileSkipped": ["members"],                       // 가로 넘침으로 건너뛴 화면
    "repoChanges": [                                    // 고쳤다 되돌린 것. 없으면 []
      { "file": "src/lib/hints.ts", "what": "교재 문구를 촬영용으로 교체", "reverted": true }

  samples 는 **실제로 써 넣은 값**을 그대로 적습니다(지어내지 마세요).
  이 프로젝트에 없는 종류(예: 사업자번호 컬럼이 없음)는 **아예 넣지 마세요** — 채우려고 만들어내면
  검사가 무의미해집니다. 담당자 쪽에서는 "그 종류를 바꾸지 않았다"는 뜻으로 읽습니다.
  담당자가 이 값을 계산해 검사합니다 — 검증코드를 통과하는 사업자번호나 정상 국번 전화번호가
  하나라도 있으면 전량 반려됩니다.
  수치는 **실제로 세어서** 적으세요 — 받는 쪽에서 파일과 대조합니다.

■ 끝내기 전 자가 점검 (여기서 걸러야 왕복이 없습니다)

  · 데스크톱 화면 15장 이상 (최소 8장)
  · 데이터 없는 화면 0장 — 채울 수 없어 건너뛴 것은 notes 에 사유
  · 차트·표·그래프 화면에 0·빈 값만 있는 것 0장
  · report.json 의 screens 수 = screenshots/ 의 png 수 (실제로 세어서 대조), 이름도 1:1 대조
  · 스크린샷 해시 중복 0건
  · scrub.samples 의 값을 직접 다시 검사 — 위 ①~⑤ 중 하나라도 걸리면 안 됩니다
  · scrub.verified = true
  · 콘텐츠 자산을 바꿨다면 원본 문구·분류 이름이 화면에 남아 있지 않은지 검색으로 확인
  · repoChanges 에 적은 수정이 **실제로 되돌아갔는지** 확인(변경 0건)
  · baseUrl 이 localhost / 127.0.0.1, 슬러그 날짜 = capturedAt 날짜
  · report.json 이 유효한 JSON (주석·후행 쉼표 없음)
  · 스크린샷 몇 장을 **실제로 열어** 확인 — 잘린 내용, 에러·환영 배너, 발주처 로고, 남은 실명·계좌

  하나라도 못 채우면 압축하지 말고 알려 주세요. 다 끝나면 만들어진 tar.gz 경로를 알려 주세요.
