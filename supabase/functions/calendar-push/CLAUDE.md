# 사내 캘린더 알림·근무지 규칙 (Claude용)

이 함수(`calendar-push`)와 화면(`dashboard/src/calendar.jsx`)은 **같은 근무지 규칙**을 따로 구현한다. 한쪽을 바꾸면 다른 쪽도 같이 바꾸고, `plan.test.ts`와 `tools/calendar-qa/`(QA 환경·점검)로 확인한다.

## 근무지 규칙
- 우선순위: 종일 휴가 > 직접 고른 개인 근무지 > 대면 미팅 외근 > 팀 근무지(그날만 정한 것 > 주간 패턴).
- 대면 미팅 외근(캘린더 미팅 '외근 표시' · 위시켓 대면 미팅): **시간 있는 미팅은 시작 시각부터 외근, 그 전엔 팀 근무지**(출근 인원에 포함, '시청역 · 14:00 외근'). 종일 미팅만 하루 전체 외근. 여러 건이면 종일 우선, 아니면 가장 이른 시각.
- 반차는 근무지를 유지하고 반차를 붙여 표시. 직접 고른 근무지가 팀 근무지와 같으면 예외가 아니다.
- '다른 장소'(loc `other` + branch): 다른 지점이나 미팅 장소로 바로 출근할 때 장소를 직접 입력. 팀·개인 모두 가능, 그날만(주간 패턴에는 못 넣음). 화면은 네이버 지도 링크.
- **미팅 장소로 아침에 바로 출근**(2026-11-05 결정): 미팅에 '바로 출근' 칸/DB 칸을 두지 않는다 — 출근 방식은 참석자마다 다르고 위시켓 미팅도 같아야 한다. 각자 그날 '내 근무' 줄의 '미팅 장소로 바로 출근'(시간 있는 외부 미팅이 있는 날만 보임)으로 개인 근무지 '다른 장소'(장소 = 미팅 장소, 메모 = '10:00 미팅 제목')를 저장 — 참석자가 여럿이면 같이 바로 가는 사람을 고른다(나만 미리 골라 둠, 다른 사람 것은 '남이 바꾼 내 근무지' 알림으로 당사자에게 감) → 위 우선순위로 처리되므로 서버 변경 없음. 화면은 반복 아닌 수동 미팅을 고치거나 지울 때 묶인 기록(그날·참석자·장소 같음)을 따라 고치거나 지운다(위시켓 미팅은 대상 아님). 시작 시각으로 바로 출근을 짐작하지 않는다.
- 그날만 정한 팀 근무지는 '이날만'이 아니라 **'평소 ○○'**(주간 패턴의 그 요일 근무지)로 표시. 평소와 같은 곳이면 표시하지 않음.

## 알림 (2026-11-03 · 11-04 사용자 결정)
- 화면: 팀 근무지에 실제로 오는 사람이 없으면 데이터는 그대로 두고 '전원 ○○'·'각자 근무'·'전원 휴가'로 표시(`teamView`). 저장 뒤 모두 같은 곳이면 '팀 근무지도 바꾸기' 제안.
- 미팅 시작 전 알림은 없다. 시간·빈도 선택 설정은 만들지 않는다(유연출퇴근 — 기본값으로 해결). 켜기/끄기 두 개만.
- **다음 근무일 안내**: 근무일 18:00~19:30 첫 실행, **매 근무일** 보냄(평소와 같아도). 제목 = 내가 갈 곳, 본문 순서 = **팀원 전원 장소별 묶음** → 팀 근무지 사유(내가 따로 가면 '팀 전체 ○○') → 내 일정. 팀원 묶음('시청역2호점: 이나래, 박다온(오후반차) · 재택: 최라온 · 연차: 한별' — 아침에 가는 곳 기준, 사람 많은 순·같으면 팀 근무지 먼저, 휴가는 뒤). 다음 근무일 종일 휴가인 사람에게는 보내지 않음(받는 사람 팀원 줄에 '연차: 이름').
- **변경 알림**: 팀원 개인 근무지·휴가·미팅 외근은 오늘~다음 근무일 → 바꾼 사람 뺀 전원. **팀 근무지는 그날 팀 근무지로 출근하는 사람에게만**(개인 근무지·종일 휴가·종일 외근이면 제외, 반차·시간 있는 미팅은 받음, 아무도 없으면 안 보냄). **남이 바꾼 내 근무지·휴가·일정은 날짜 상관없이 당사자에게**(일정은 참석자 + 만든 사람, 1년 안 회차). 주간 패턴(8일 안에 실제로 쓰임, 내용이 바뀐 경우만) → 전원. 일정 → 참석자(전·후)·만든 사람. 밤 22:00~07:30 은 아침으로 미룸.
- 같은 대상을 한 실행 안에서 여러 번 바꾸면 처음·끝만 비교(지웠다 되돌림은 안 보냄). 반복 일정 나누기 짝은 같은 사람·15초 이내로 판단(감사 번호 차이 금지 — 다른 표 기록이 끼어든다). 화면은 나누기를 `calendar_split_event` RPC 한 번(한 트랜잭션: INSERT→UPDATE)으로 저장한다(2026-11-06) — 짝 판단은 그대로 맞는다.
- 같은 실행의 안내를 받는 사람에게, 다음 근무일에 대한 **18:00 전** 변경 알림은 생략(안내에 담김). 18:00 이후 변경은 보냄 — 알림이 빠지는 쪽으로 줄이지 않는다.

## 알림 문구 원칙
- 제목 = 누가/무엇이 어떻게(바뀐 곳·일정 이름 포함). 본문 = 언제 · 바뀐 것 · 이유 · 바꾼 사람(당사자와 다를 때만, 동사 맞춤: 추가/변경/취소).
- 쓰지 않는다: 제목을 본문에서 반복, 보내는 규칙 설명('(평소와 다름)'·'(계속)'), 다 나열하면서 붙이는 건수, '패스트파이브'·'재택근무'의 '근무', '— 누군가', 제목에 날짜가 있을 때 본문 날짜.
- 아침에 갈 곳이 먼저: 오후 미팅이 있는 날 본인 안내 제목은 '🏢 내일 시청역2호점 · 14:00 외근 (…)'.

## 운영
- 5분마다 pg_cron → 이 함수. 근무지·휴가·일정은 400일 앞까지 읽는다(먼 날 당사자 알림의 상태 계산용). 실행마다 `push_state.heartbeat` 기록 → `calendar_push_status()` RPC → 화면이 30분 넘게 끊기면 캘린더에 경고, 설정 창에 마지막 실행 표시.
- 발송 결과(`pushOutcome`, 2026-11-05): 404/410 → 구독 삭제 · 429/5xx/네트워크 → `push_state.retry_queue` 에서 최대 6번 재시도 · 그 밖의 4xx(401·403 등) → 재시도·삭제 없이 기록만(heartbeat `rejected`).
  일시 실패로는 구독을 지우지 않는다 — 실패 30번 이상 + 14일 넘게 못 받은 구독만 정리(`isStaleSub`).
- 알림 키(push_sent)를 잡은 뒤 **보내기 전에 대기열에 먼저 적는다** → 도중에 죽어도 다음 실행이 보낸다(드물게 중복, 유실 없음).
- 실행 잠금 `push_state.run_lock`: 한 번에 하나, 3분 안 재실행은 `{skipped:'busy'}`(공개 anon 키 연타로 재시도 소진·대기열 덮어쓰기 방지). 수동 시험은 run_lock 의 until 을 과거로 바꾼 뒤 호출.
- 상태 저장(setState) 실패는 오류로 끝낸다. 500 응답 본문엔 원문 오류를 싣지 않는다(로그에만).
- 클라이언트는 `push_subscriptions` 에서 알림 켜기/끄기 두 칸만 고칠 수 있다(등록·이전은 `register_push_subscription` RPC).
- 배포: 함수는 `supabase functions deploy calendar-push`(verify_jwt 유지), 테스트는 `deno test plan.test.ts`(Homebrew deno 는 소스 빌드라 느림 — 공식 바이너리 `~/.deno-bin/deno`).
- 주간 패턴 변경 알림: 바꾸기 전·후 패턴으로 앞으로 8일 팀 근무지를 비교해 달라지는 날만(같은 내용 재저장 생략, 예정 취소 DELETE 도 알림).
