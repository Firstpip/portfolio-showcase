# 📊 모드: admin-dashboard (백엔드 중심 공고 폴백)

이 공고는 **백엔드·데이터 처리**가 핵심이라 눈에 보이는 화면이 원래 없다. API·배치·연동 자체는 데모로 보여줄 수 없으므로, **"입력 → 처리 → 결과"를 눈으로 확인하는 운영자 대시보드**로 시연한다.

보는 사람이 얻어야 할 인상: "이 팀은 우리 데이터가 어떻게 흘러가고 무엇이 좋아지는지 이해하고 있다."

## 화면 구성 (이 순서를 지켜라)

1. **상단 KPI 카드 3~4개** — 처리 건수, 성공률, 평균 처리시간, 개선폭 같은 숫자. 큰 숫자 + 작은 라벨 + 전기간 대비 증감.
2. **실행/입력 영역** — 이 공고의 핵심 처리를 사용자가 직접 돌려보는 곳. 예: 파일·텍스트 입력, 대상 선택, "실행" 버튼. tier 1 flow 라면 여기서 실제로 store 를 갱신한다.
3. **결과 영역** — 실행 결과를 표가 아니라 **읽히는 형태**로. 처리 전/후 비교, 항목별 상태 배지(성공·경고·실패), 소요시간.
4. **최근 이력 목록** — 시드 데이터 기반. 각 행에 시각·대상·상태·소요시간.

## 반드시 지킬 것

- **"처리 중" 을 연출하라.** 실행 버튼 → 0.8~1.5초 가짜 지연 → 결과. 즉시 나오면 아무것도 안 한 것처럼 보인다. 진행 표시(스피너 또는 단계 텍스트)를 함께 보여준다.
- **숫자에 맥락을 붙여라.** "1,284" 만 있으면 의미가 없다. "1,284건 처리 · 전주 대비 +12%" 처럼.
- **상태는 색으로 구분.** 성공/경고/실패를 배지로. 빨강·노랑·초록을 남발하지 말고 각 1회씩.
- 표가 필요하면 컬럼 5개 이하. 그 이상은 카드 리스트로.

## 차트

- **차트 라이브러리는 이번 스택의 허용 패키지 목록에 있을 때만 쓴다** (React 계열엔 `recharts` 가 있고, Vue 계열엔 **없다**). 목록에 없으면 절대 새 패키지를 import 하지 마라 — 빌드가 깨진다.
- 라이브러리가 없으면 **CSS 로 그려라**: 높이 비율을 준 막대 `div`, 가로 진행바, 도넛 대신 숫자+진행바. 이게 오히려 가볍고 안전하다.
- 차트는 최대 1~2개. 대시보드는 차트 전시장이 아니다.

## 하면 안 되는 것

- 실제 API 호출·외부 연동 (전부 시드 + LocalStorage)
- 로그인·권한 관리 화면 (공고의 핵심이 아니면 만들지 마라)
- 의미 없는 더미 그래프로 화면 채우기
